## 一句话结论

NeocorRAG 想补的是检索增强生成（Retrieval-Augmented Generation，RAG）里经常被混在一起的两件事：**找到了支持材料，和模型真的能用这些材料答对，并不是一回事。**

它的做法是先从召回文档对应的图里找候选路径，让语言模型在这些路径里选证据链，再用链条筛文档、辅助回答。思路很具体，也有实验收益。我更愿意把它看成一种检索后的上下文处理方法，而不是又一个“给 RAG 加图”的故事。

但论文的几层保证不能连着往上推：只能生成候选里的链，不代表候选里的事实正确；答案 F1 提高，不代表证据用得更忠实；过滤后答案更好，也不代表没有丢掉支持材料。

**方法值得学，解释结果时得比论文的宣传语克制一点。**

## 它想解决什么问题

常见的 RAG 优化从检索器入手：让标准支持段落尽量出现在前几个结果里。问题是，Recall 只看材料有没有进来，不看一起进来的其他东西会把模型带到哪里。

论文反复用一个多跳问题说明这件事：《The Newcomers》的一位演员因什么而知名？电影页面列出演员，人物页面说明 Chris Evans 以超级英雄角色知名。模型得把“电影—出演者”和“演员—知名角色”接起来，答案才出来。其他同样提到电影或演员的段落，可能只是无关，也可能把推理引向错误的人或作品。支持文档都在，Recall 可以相同，答案却不一定相同。（原文图 1、图 3）

作者为此提出 Recall Conversion Rate（RCR，召回转化率）：Recall 大于零时，取答案 F1 与 Recall 的比值；为零时记为零。比如 F1 是 60、Recall 是 80，按百分数展示的 RCR 就是 75。（原文 §3.1、式 1）

这个指标的提醒是有用的：别只看检索端，要一起看回答端。但名字容易让人多想一步，仿佛它真的测出了“召回的证据有多少被正确使用”。这个解释并不成立，后面再说。

问题本身倒不需要依赖新指标才能成立。材料之间的关系没组织好、无关上下文太多，即使检索器已经把支持文档送到了，也还有优化空间。NeocorRAG 就在这个空间里动手。

## 方法

三个步骤，分别处理候选空间、选链和最终上下文。

1. **先搜出候选链，别让模型从零编。** 从问题中抽取实体，在初始召回文档对应的子图里定位起点，再做带剪枝的深度优先搜索。每一跳计算三元组和问题的相关性，太低就不继续扩展。路径评分还看整链相关性、高置信关系，以及超过期望长度后的衰减。不是无条件偏爱短链，而是限制没有必要的绕路。（原文 §3.3.1）
2. **把候选链放进前缀树，约束模型的下一步。** 候选链序列化之后，相同开头合并成共享前缀。模型仍然给 token 打分，但不属于合法后继的 token 会被屏蔽，再通过束搜索保留多条链。这里约束的是 token 序列，不是让模型每次直接挑一个图节点。它能防止自由生成候选外的路径，不能修复候选图本身的错误。（原文 §3.3.2）
3. **用选中的链筛文档，再把文档和链一起交给回答模型。** 初始排名靠前的文档默认保留，低排名文档要检查是否包含选中链里的三元组。附录参数里默认保留前两篇，所以它也不是“只留下通过证据链检查的材料”。最终输入仍有原文，链条没有取代原文。（原文 §3.3.3、表 5）

图在语料入库时构建，查询相关的路径搜索仍然在线进行。这里的“无需额外训练”，也只是不用为这套流程再训练模型，不等于没有建图、抽取和维护成本。（原文附录 E）

结果先看最容易核对的一组。原文表 1 在 **70B 回答模型**条件下报告四个数据集的平均结果：HippoRAG2 的答案 F1 是 64.6；NeocorRAG 用 3B 辅助模型选链时是 66.1，用 8B 时是 68.1，分别高 1.5 和 3.5 点。这里的 3B、8B 是选链模型，不是最终回答模型。

另一组对照更贴近它的动机：Trace 3B 和 NeocorRAG 3B 的平均初始 Recall 都是 84.5，答案 F1 分别为 52.7 和 66.1。至少在这组设置里，初始材料相同水平，后面的处理确实还能拉开差距。不过这不是只改一个组件的对照，13.4 点不能全记到约束解码头上。

消融实验给了进一步依据：在 HotpotQA、3B 回答设置下，完整方法 F1 为 66.8，换成朴素链搜索后为 49.5，去掉约束解码为 58.7，去掉文档过滤为 57.0。几个组件都有贡献，但消融差值不能相加，它们会改变彼此接到的输入。（原文表 2）

成本也有亮点。图 4 里，3B 辅助模型配置下每题 token 消耗是 1.90k，Trace 对应 64.26k，约为后者的 3%。这是具体对照下的 token 数，不代表整套系统的费用也只剩 3%，更不能直接换算成端到端加速倍数。

## 我的疑问

**RCR 更像诊断用的比值，不像它名字暗示的“转化率”。** 答案 F1 衡量的是与标准答案的词级重合，Recall 衡量的是标准支持段落的覆盖，两者不是同一批事件的成功数和总数。模型还可能靠参数知识答题，或者只用部分证据就猜对。原文主表里确实有超过 100 的 RCR，这已经足以说明它不是一个概率。

分母效应也绕不过去。F1 不变，只要 Recall 下降，RCR 就会上升。再拿 Recall 和 F1/Recall 画相关图，横纵轴还共享同一个变量。因此，“Recall 越高，RCR 越低”这个现象本身，不能证明高召回导致了更多干扰。我要判断方法有没有用，仍然会先看相同配置下的 F1 和 Recall，再看引用是否真的支持答案，而不是只看一个比值。

**过滤是有代价的，表 3 比结论里的措辞更值得记住。** 平均文档数从 5.00 降到 3.52，非标准支持文档数从 2.83 降到 1.39；与此同时，Recall 从 84.53 降到 80.61，少了 3.92 点。NQ 上下降更明显，是 9.34 点。

这不自动否定过滤。少一些材料，答案反而更好，完全可能是一笔划算的交换。但这笔交换得承认，不能把主表里的初始 Recall 当成过滤后的 Recall，然后说方法没有召回损失。表里的 AID 又是按标准支持集合统计的，非标准支持文档并不逐篇等于有害文档。删掉多少“非标准材料”和删掉多少“干扰”，不是同一件事。

（表 3 的部分 RCR 数值与主表 F1、过滤后 Recall 的对应关系也不够清楚。这份笔记不替作者猜统计口径，只保留能直接读出的文档数和召回变化。）

**前缀树给的是候选约束，不是真实性保证。** 一条错误关系只要先被抽进图，就能成为合法候选；只要它在候选里，约束解码就完全可能忠实地选出它。实体同名、关系方向抽反、不同年份的事实混在一起，都不是“屏蔽非法 token”能解决的。

反过来也一样。关键关系没被抽出来，候选空间里就没有那条边。后面的模型再会选，也选不出不存在的路径。所以这套方法把一部分不确定性前移到了建图和候选搜索，而不是把不确定性消掉了。式 8 对文档与三元组的匹配又采用字符串包含的形式描述，实体别名和关系改写如何处理，还需要看实现，不能自行把它理解成完善的语义蕴含检查。

**和 GraphRAG 有联系，但不是拿来就能拼。** 这里需要先分清泛称的图增强 RAG 和 Microsoft 的同名工作。后者的[原始论文](https://arxiv.org/abs/2404.16130)重点处理全局语料总结，通过实体关系图、社区摘要和查询时的汇总组织答案；NeocorRAG 主要解决当前问题下的局部事实问答。两者都用图，不代表做的是同一道题。

原文没有直接证明 NeocorRAG 比 Microsoft GraphRAG 更好，也没有验证两者组合的收益。一个值得试的接法，是让已有图提供候选实体和原文段落，再加局部选链与过滤。但如果只把社区摘要交过去，细粒度关系可能早被压缩掉了；如果任务本来就是全局总结，收紧到少数几条链又可能损失主题覆盖。

真要接进项目，我会先固定查询、语料快照和回答模型，保存初始文档、候选链、选中链、最终文档，再对比答案质量、支持段落保留情况和端到端延迟。否则结果变差时，很难知道该怪检索、建图、选链，还是最后那次过滤。这是后续验证思路，不是已经做过的实验。

**还有一处基线引用需要悬置判断。** 正文把 CoRAG 描述成训练得到的动态检索链，参考文献 [39] 却指向成本约束检索工作。后者是 [arXiv:2411.00744v1](https://arxiv.org/abs/2411.00744v1)，而 Chain-of-Retrieval Augmented Generation 是另一篇 [arXiv:2501.14342](https://arxiv.org/abs/2501.14342)。仅凭论文不能确认表中采用的具体实现，所以这里主要看 HippoRAG2 和 Trace 的对照，不拿那一列撑结论。引用对应不清是需要核实的问题，不是可以直接推导出实验失效的证据。

## 值得记住的点

- **检索和上下文组织是两个优化位置。** 支持文档已经召回，不代表后面只能换一个更大的回答模型；组织关系、筛选材料同样有空间。
- **约束解码的上限由候选集合决定。** 它能管住模型往哪里走，管不住地图最初画得对不对。建图错误和解码错误要分别查。
- **给指标起一个直观名字，不会自动赋予它那个含义。** F1/Recall 可以辅助比较，却不是证据利用率，更不是因果解释。
- **上下文变短的收益，要和支持材料损失一起算。** 过滤前后都报 Recall，才知道答案提升用了什么代价。
- **可解释的链最好能点回原文。** 显示一条流畅的关系链还不够，来源段落、关系方向和时间条件能被核实，解释才有实际用处。

这篇最值得带走的，不是“图让 RAG 更可靠”，而是一个更具体的工程思路：**把检索后的上下文处理拆成可检查的步骤。至于每一步是否可信，还得分别验证。**
